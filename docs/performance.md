# 1 核 1G 优化与验证记录

## 已实现

- 单进程 Waitress，4 个请求线程，64 个连接，2MiB 请求体上限；显式启停调度器与进程锁。
- SQLite 持久化执行队列，全局最多 32 个未完成任务，HTTP 并发 2、脚本并发 1。账号级去重，随机和重试等待不占线程。
- 排队任务重启后恢复；执行中崩溃的任务写入中断日志，避免自动重复执行。修改或删除账号使旧执行失效。
- HTTP 流式读取，压缩前后双重字节限制，限次重定向，网络 socket 总时长监控。操作系统 DNS 解析阶段不受 socket 关闭控制，依赖系统解析器的超时设置。
- 脚本输出通过有界管道捕获；墙钟超时、进程树 RSS/数量监测、Node 堆限制、Linux CPU/FD/Python 地址空间限制；支持可选 cgroup v2 硬内存限制。
- 按渠道持久化通知，独立线程、有限队列、退避重试。业务签到成功与通知失败互不耦合。
- WAL、有限 busy_timeout、小缓存、旧库显式索引迁移。保持 synchronous=FULL。
- 日志查询字段裁剪、列表响应摘要、详情按需加载、分页参数上限；账号摘要分页与单账号编辑接口。
- 批量配置读写、合并统计聚合、流式导出和分批导入。
- 默认启用日志清理，短批次、有每轮时间预算；执行和通知历史独立清理。Compose 资源额度和日志轮转。

## 实测

2026-09-20，Windows Python 3.14.2、WSL Ubuntu 22.04 Python 3.10.12。测试不访问生产数据库、真实签到地址或通知渠道。

- Linux：36/36 测试通过。
- Windows：33 项通过，3 项 Linux 专用测试跳过。
- JavaScript 语法检查与 `git diff --check` 通过。
- Chrome 独立测试库验证：21 个账号分页、单账号脚本编辑回填、手动任务从提交到成功、按钮恢复、2014 字符日志详情弹窗；最终控制台无错误。

功能及资源测试包含：并发提交去重、队列溢出、24 个积压任务、重试释放线程、账号版本失效、删除重建账号、崩溃恢复、SQL 查询计划、配置事务、通知分渠道重试、大响应、gzip 解压上限、慢速响应头/正文、脚本过量输出、内存监测、Linux 派生进程回收、生产入口单实例和 SIGTERM 退出。

单 CPU 冒烟压测命令：

```bash
python tests/benchmark_profile.py
```

该脚本启动临时 Waitress 服务，并设置服务的 CPU affinity 为一个逻辑 CPU，子进程继承。提交 24 个任务：16 个本地 HTTP（模拟 150ms 延迟）、8 个 Python（分配 16MiB、等待 200ms），同时查询管理接口。

| 指标 | 本次结果 |
|---|---:|
| 成功完成任务 | 24/24 |
| 提交至全部完成 | 2.767 秒 |
| 服务与脚本进程树采样峰值 RSS | 69.8MiB |
| 最大进程数（服务 + 脚本） | 2 |
| 账号列表请求样本 | 32 |
| 账号列表请求中位延迟 | 4.22ms |
| 账号列表最大延迟 | 15.88ms |

另一生产生命周期测试中，运行一个简单脚本后的服务进程 RSS 为 43.9MiB。

这些数据是特定模拟负载下的观测值，不是容量承诺。此环境没有 Docker daemon，未实际构建 Alpine/Python 3.11 镜像，也没有施加 1GiB 整机 RAM/cgroup 配额；不能将 CPU affinity 测试称为完整 1 核 1G 压测。严格 cgroup 脚本限制需要部署主机提供委派目录，本次验证了常规资源监测和 Linux 进程回收路径。

## 上线检查

1. 先正常停止旧服务并备份数据目录；在构建机/CI 重建镜像，用仓库 Compose 启动。不要多个进程共用同一目录。
2. 已有数据库保留原日志开关，在系统设置中确认自动清理开启，建议保留 500～1000 条。
3. 校验 `/health`、登录、单次 Curl/Python/JavaScript 执行、失败重试与通知状态。队列满时手动提交应得到 429，而不是无限新增线程。
4. 观察真实负载下的容器峰值内存、CPU、接口延迟、任务等待、失败日志及 SQLite/WAL 文件增长。脚本 RSS 监测有采样间隔；需要严格进程树额度时提供 cgroup v2 委派。
5. 在线备份使用 SQLite backup API；不要在服务运行时只复制主 DB 文件而忽略 WAL。

任务积压与迟到策略：APScheduler 触发允许迟到 5 分钟；已成功入队的待执行项及重试会持久化并在资源可用后执行，包括服务恢复后的逾期项。随机窗口用于选择初始计划时间，不保证故障/积压后的实际执行仍在窗口内。对于已经开始的外部请求，无法提供事务式撤回或严格 exactly-once 保证。
